# Audit endpoint — 2 November 2026

Status: **masih ada celah**. Audit ini tidak mengubah kode aplikasi. Lima temuan keamanan/integritas dan dua regresi fungsi dipisahkan di bawah. Prioritas memperhitungkan bahwa beberapa operasi hanya dapat dilakukan administrator berizin; bukan semua temuan dapat dieksploitasi tanpa login.

## Cakupan dan bukti

- Inventaris runtime: **305 endpoint**, terdiri dari 243 administrator, 41 member, 16 publik/capability, dan 5 dokumen dengan pemeriksaan pemilik/capability.
- **809 pemeriksaan HTTP** terhadap router aplikasi: 284 tanpa token, 284 dengan jenis principal yang salah, 241 administrator tanpa izin menu. Seluruhnya ditolak 401/403; tidak ada query database yang tidak diizinkan dalam harness. Dua endpoint profil administrator memang hanya membutuhkan autentikasi, sehingga tidak dimasukkan dalam 241 pemeriksaan izin menu.
- JWT verification dan middleware aplikasi asli dipakai; akun dan sesi diganti fixture. Ini menguji pagar akses, bukan seluruh kombinasi izin positif atau kepemilikan setiap record.
- Inventaris dan hasil per endpoint: [audit-2026-11-02-endpoints.json](audit-2026-11-02-endpoints.json). Tidak adanya kolom `checks` berarti endpoint tidak termasuk matriks penolakan di atas, **bukan berarti aman**.
- Tes proyek: `cd server; npm.cmd test -- --runInBand --silent` → **25 suite, 147 tes lulus**.
- Reproduksi tambahan: `node doc/security/audit-2026-11-02-repro.cjs` dari root → tujuh skenario terbukti. Script menjalankan kode sumber dengan mock database, penghapusan file, dan WhatsApp; tidak mengubah data riil.
- Penelusuran difokuskan pada autentikasi/refresh/OTP/registrasi, pemetaan izin, profil/ownership member, dokumen privat, unggahan, keputusan bantuan dan realisasi; pencarian lintas source juga mencakup query mentah, pemanggilan HTTP eksternal, dan rendering HTML.
- **Tidak ada build** karena ini audit. Tidak melakukan pengujian produksi, uji OOM, transfer uang, ataupun pembuktian konkurensi pada MySQL nyata. Konfigurasi reverse proxy luar repository, migrasi yang benar-benar terpasang, dan advisori dependency terbaru belum diverifikasi.
- Pemeriksaan mendalam alur bisnis tidak setara untuk seluruh 305 endpoint; laporan ini tidak menyatakan semua endpoint sudah bebas celah atau semua kombinasi input telah diuji.

## SEC-01 — Tinggi: member dapat menghapus permohonan tanpa pembatasan tahap realisasi

Endpoint: `POST /riwayat_permohonan_member/delete`.

Prasyarat: login sebagai member pemilik permohonan. Tidak memerlukan izin administrator.

Sumber:

- `server/router/router_riwayat_permohonan_member.js`: hanya validasi bentuk `id` pada operasi hapus.
- `server/modules/riwayat_permohonan_bantuan/models/model_cud.js:25–55`: cek pemilik, kemudian `Permohonan.destroy`; tidak membaca status realisasi, tahap verifikasi, ataupun pembayaran.
- `server/migrations/20250907073150-create-realisasi-permohonan.js:12–18`: foreign key realisasi ke permohonan memakai `ON DELETE CASCADE`.
- `server/migrations/20250907085129-create-validasi-syarat-permohonan.js`: validasi syarat ikut cascade dari realisasi.

Langkah reproduksi pada database uji terisolasi:

1. Buat member A dan permohonan miliknya.
2. Buat realisasi terkait dengan status `approve` dan `status_realisasi=sudah_direalisasi`.
3. Gunakan record tanpa referensi lain yang memakai foreign key RESTRICT, misalnya tanpa survei/monev. Referensi RESTRICT dapat menggagalkan penghapusan untuk sebagian record, sehingga dampaknya tidak berlaku identik pada semua permohonan.
4. Login sebagai A dan kirim `{ "id": ID_PERMOHONAN }` ke endpoint hapus.
5. Kode mengizinkan DELETE. Dengan skema migration tersebut, realisasi dan validasi syarat terkait ikut terhapus. Pelaku dapat menghilangkan riwayat penyaluran miliknya dan memengaruhi laporan yang menghitung tabel tersebut.

Bukti offline `member-delete`: DELETE benar-benar diminta oleh model tanpa pemeriksaan realisasi. Efek cascade ditetapkan dari migration; belum dieksekusi pada database riil. Ini bukan IDOR lintas member: cek pemilik sudah ada. Masalahnya adalah pemilik diberi kewenangan menghapus catatan yang seharusnya sudah menjadi riwayat administrasi/keuangan.

Perbaikan:

1. Tetapkan tahap awal yang boleh dibatalkan member; tolak jika sudah diverifikasi, disurvei, disetujui, atau direalisasi.
2. Terapkan pembatalan dengan mempertahankan histori, bukan hard delete terhadap permohonan yang sudah diproses.
3. Periksa dan kunci record dalam transaksi yang sama dengan perubahan; selaraskan dengan transaksi persetujuan/realisasi agar tidak ada celah waktu.
4. Tambahkan tes pemilik dengan realisasi final ditolak, nonpemilik ditolak, dan pembatalan tahap awal mengikuti aturan yang dipilih. Jangan langsung mengganti seluruh cascade tanpa audit migration dan data lama.

## SEC-02 — Sedang: mengganti satu berita acara menghapus file yang masih dipakai record lain

Endpoint:

- `POST /bakal_penerima_bantuan/upload_berita_acara_massal`
- `POST /bakal_penerima_bantuan/upload_berita_acara`

Prasyarat: administrator berizin distribusi (`menuId=2`, `submenuId=3`). Dapat terpicu oleh tindakan normal, tanpa niat menyerang.

Sumber: `server/modules/bakal_penerima_bantuan/models/model_cud.js`, metode `upload_berita_acara_massal`, `upload_berita_acara`, dan `response` (sekitar baris 154 dan 336).

Langkah:

1. Unggah berita acara massal untuk realisasi A dan B yang memenuhi syarat. Kedua row memakai filename yang sama.
2. Ganti berita acara A melalui endpoint unggah tunggal.
3. Transaksi A commit, lalu `response()` menghapus filename lama tanpa memeriksa apakah B masih merujuk file itu.
4. Row B tetap menunjuk file lama, tetapi dokumennya hilang. Pengunduhan dokumen B menjadi gagal.

Bukti offline `shared-document-delete`: row B tetap merujuk `shared.pdf`, sementara helper penghapusan menerima `shared.pdf` setelah penggantian A.

Perbaikan:

1. Jadikan referensi file bersama sebagai invariant yang dijaga pada penggantian dan pembatalan.
2. Hapus hanya setelah commit dan setelah dipastikan tidak ada referensi lain **di seluruh record**, bukan hanya kegiatan yang sama. Tangani konkurensi atau gunakan pembersihan orphan terpisah yang memverifikasi ulang.
3. Tambahkan tes upload massal A/B → ganti A → file B tetap tersedia, serta penghapusan referensi terakhir.
4. Tinjau pola serupa pada file syarat bulanan (`validasi_permohonan_bantuan` menyalin path). Pola itu ada di source, tetapi alur persetujuan saat ini juga terhambat REG-02; jangan menganggapnya sudah dibuktikan end-to-end.

## SEC-03 — Sedang: kegagalan acknowledgement COMMIT dapat menghapus bukti yang sudah tercatat

Endpoint yang ditelusuri:

- `POST /bakal_penerima_bantuan/realisasi_bantuan`
- `POST /bakal_penerima_bantuan/upload_berita_acara`
- `POST /bakal_penerima_bantuan/upload_berita_acara_massal`
- Pola tambahan pada `POST /validasi_permohonan_bantuan/edit_file`.

Prasyarat: operasi unggah sah oleh admin dan kegagalan koneksi/respons database pada commit. Ini kelemahan integritas saat gangguan, bukan bukti bahwa member dapat sengaja memutus koneksi database.

Sumber:

- `server/validation/bakal_penerima_bantuan.js:253–255`: event `finish` menghapus file pada semua respons HTTP >=400.
- `server/modules/bakal_penerima_bantuan/models/model_cud.js:330`: commit langsung; tidak membedakan hasil yang belum pasti.
- `server/modules/bakal_penerima_bantuan/controllers/index.js`: exception commit menghasilkan respons error.
- `server/modules/validasi_permohonan_bantuan/controllers/index.js`: catch `edit_file` juga langsung membersihkan unggahan.

Langkah:

1. Unggah bukti sah dan simpan nama file dalam transaksi.
2. Simulasikan database telah menerapkan COMMIT, tetapi acknowledgement ke aplikasi hilang.
3. Promise commit menolak; controller membalas 500.
4. Hook `finish` menghapus file baru, padahal row yang sudah commit merujuk file tersebut.

Bukti offline `commit-uncertainty`: `simulatedDatabaseCommitted=true`, HTTP 500, penghapusan `committed.pdf` dipanggil oleh middleware asli. Penghapusan filesystem dimock.

Perbaikan:

1. Jangan menjadikan kode status HTTP sebagai satu-satunya dasar penghapusan upload.
2. Bersihkan file apabila validasi gagal sebelum transaksi atau rollback telah pasti berhasil.
3. Jika commit/rollback belum pasti, pertahankan file dan tandai untuk rekonsiliasi; jangan meminta pengguna mengulang tanpa pemeriksaan hasil.
4. Gunakan pola yang sudah ada pada model survei/permohonan member, dengan kepemilikan cleanup yang jelas; audit seluruh hook cleanup agar tidak menghapus file lagi dari lapisan lain.
5. Uji tiga keadaan terpisah: rollback pasti, commit pasti, dan commit/rollback tidak pasti.

## SEC-04 — Sedang: pemeriksaan status realisasi tidak atomik dengan pembaruan

Endpoint: `POST /bakal_penerima_bantuan/realisasi_bantuan`; periksa juga konsistensi dengan `batal_realisasi`.

Prasyarat: administrator berizin distribusi, dua permintaan yang beririsan.

Sumber:

- `server/validation/bakal_penerima_bantuan.js:29`: membaca status sebelum transaksi model, tanpa row lock.
- `server/modules/bakal_penerima_bantuan/models/model_cud.js:81–84`: UPDATE hanya menggunakan `where: { id }`, tanpa status sebelumnya atau pemeriksaan jumlah row yang berhasil diklaim.

Langkah:

1. Siapkan realisasi disetujui, belum direalisasi.
2. Request A dan B sama-sama melewati validator saat status masih `belum_direalisasi`.
3. A memperbarui bukti/nominal dan commit.
4. B tetap melakukan UPDATE terhadap ID yang sama, menimpa hasil A, lalu ikut sukses.
5. Jika notifikasi diminta, kedua proses dapat mengirim pemberitahuan. Audit tidak mengirim WhatsApp.

Bukti offline `realisasi-stale-validation`: dua panggilan validator lolos, dua UPDATE diterima, dua respons model sukses. Ini simulasi urutan eksekusi yang mungkin terjadi, bukan uji beban MySQL. Tidak ada bukti transfer uang ganda: endpoint ini mencatat realisasi, tidak memanggil API bank untuk melakukan transfer.

Perbaikan:

1. Kunci row realisasi dalam transaksi dan periksa status serta batas nominal dari row terkini.
2. Gunakan conditional UPDATE dengan status yang diharapkan dan wajibkan tepat satu row berubah.
3. Koordinasikan aturan yang sama pada pembatalan/perubahan keputusan.
4. Kirim notifikasi setelah commit yang pasti; gunakan mekanisme retry yang tidak menggandakan notifikasi.
5. Tambahkan tes interleaving dua realisasi serta realisasi versus pembatalan.

## SEC-05 — Sedang: multipart survei tidak membatasi jumlah field teks

Endpoint: `POST /survey_lapangan/submit`.

Prasyarat: sesi capability survei sah. Pengguna tanpa capability sudah ditolak sebelum parsing file.

Sumber: `server/validation/survey_lapangan.js:164–172`. Batas hanya `fileSize` dan `files`; tidak ada `fields`, `parts`, atau batas agregat body. Batas JSON 1 MB pada `app.js` tidak membatasi multipart. Konfigurasi proxy dalam repository tidak menetapkan batas kecil khusus endpoint ini; konfigurasi proxy eksternal belum diverifikasi.

Langkah dan bukti aman:

1. Kirim multipart dengan 80 field teks tak terpakai, masing-masing 16 KiB, tanpa file.
2. Parser survei asli menerima seluruh 1.25 MiB teks sebelum validator bisnis berjalan.
3. Skenario `survey-unbounded-text-fields` membuktikan 80 field lolos parsing. Respons 200 pada harness berasal dari handler inspeksi setelah parser, bukan klaim bahwa endpoint bisnis menerima survei tidak lengkap.
4. Jumlah field tidak dibatasi aplikasi; memperbesar payload dapat menekan memori proses sebelum request ditolak oleh validator. Rate limit jumlah request tidak membatasi konsumsi satu request. Tidak melakukan uji sampai crash/OOM.

Perbaikan:

1. Batasi jumlah field/parts berdasarkan field formulir yang benar-benar diperlukan.
2. Batasi ukuran per field teks serta total request pada ingress; bedakan kebutuhan 12 file gambar dari field teks.
3. Tambahkan tes satu field melebihi batas, terlalu banyak fields/parts, serta formulir normal tetap berhasil.
4. Audit konfigurasi parser `pengaturan_umum` yang juga hanya menetapkan `fileSize`; dampak endpoint tersebut belum direproduksi dalam laporan ini.

## REG-01 — Regresi fungsi dan inkonsistensi scope: identitas survei hilang setelah multipart

Endpoint: `POST /survey_lapangan/submit`.

`requireSurveyCapability` mengisi `req.body.access_code` dari cookie terverifikasi (`server/helper/surveyCapabilityHelper.js:122`), tetapi middleware upload berjalan setelahnya (`server/router/router_survey_lapangan.js:77`). Multer mengganti body, sehingga trusted code hilang atau diganti field dari client. Validator dan model masih membaca `body.access_code`, bukan `req.surveyCapability`.

Reproduksi `survey-multipart-regression`: capability ID 1 tetap ada, tetapi access code berubah menjadi `client-code`; ketika field code tidak dikirim, nilainya null setelah parser. Frontend sekarang tidak menyertakan kode pada formulir submit (`client/src/views/SurveyLapanganView.vue`, bagian FormData).

Dampak yang terbukti: formulir sah kehilangan kode yang dibutuhkan downstream. Scope cookie dan scope input bisa berbeda. **Belum ada bukti akses kegiatan lain tanpa mengetahui access code aktif kegiatan tersebut**, karena validasi downstream masih memeriksa kode itu. Karena itu tidak dilaporkan sebagai bypass autentikasi tinggi.

Perbaikan: validator/model memakai ID capability terverifikasi langsung, atau pulihkan nilai tepercaya setelah parsing dari properti request internal. Jangan mengambil identitas otorisasi dari field multipart. Tambahkan tes router utuh dengan multipart, termasuk code dihilangkan dan code palsu disertakan.

## REG-02 — Regresi fungsi: persetujuan/penolakan valid gagal karena `Op` tidak diimpor

Endpoint: `POST /validasi_permohonan_bantuan/approve_permohonan` dan `.../reject_permohonan`.

Source `server/modules/validasi_permohonan_bantuan/models/model_cud.js` memakai `Op.ne` (baris 318) dan `Op.in`, tetapi destructuring `../../../models` pada awal file tidak menyertakan `Op`.

Reproduksi `approval-regression`: permohonan dalam status `process` menghasilkan `Op is not defined`, state gagal. Tes yang ada hanya memeriksa penolakan operasi terhadap status final, sehingga berhenti sebelum mencapai referensi `Op` dan tetap lulus.

Perbaikan: gunakan import operator Sequelize yang sudah menjadi pola repository dan tambahkan happy-path approval/rejection. Setelah itu, periksa generator bantuan bulanan: loop membuat semua bulan berikutnya setiap kali record bulanan disetujui tanpa pemeriksaan eksistensi periode. Risiko duplikasi tersebut terlihat di source tetapi belum dapat dinyatakan sebagai eksploitasi alur berjalan karena saat ini terhalang error `Op`.

## Urutan tindak lanjut

1. Tutup SEC-01 terlebih dahulu untuk menjaga histori keuangan dari penghapusan member.
2. Perbaiki SEC-02/03 dan audit file yang sudah kehilangan referensi fisik; pemulihan mungkin membutuhkan backup.
3. Perbaiki SEC-04/05 dan kedua regresi, lalu uji kasus positif serta negatif yang dijelaskan.
4. Konfirmasi perilaku pada MySQL terisolasi dengan migration yang sama dengan deployment, khususnya cascade dan konkurensi.
5. AI pelaksana dapat memakai langkah dan script reproduksi di atas; kerjakan perubahan rutin tanpa banyak pertanyaan. Jangan menyentuh data produksi atau mengarang keberhasilan pengujian. Jika perlu build untuk implementasi, jalankan **sekali di akhir**, setelah seluruh perubahan dan tes terarah selesai.
